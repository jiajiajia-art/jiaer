## 1. 系统提示词（原「剧本基调」）长度

| 项 | 旧 | 新 |
|---|---|---|
| 字段 | `content.prompt.scriptTone`（字段名**不变**） | 同左 |
| 编辑器硬上限 | 5000 字 | **8000 字** |
| AI 生成目标 | 1500–3000 字 | **3500–4500 字（约 4000）** |
| 前端常量 | `Romance/src/lib/modBasicInfoLimits.ts` → `SCRIPT_TONE_MAX` | 同左 |

后端需要：
- 草稿保存、发布审核、作品详情等接口如有长度校验，`scriptTone` 放宽到 **≥ 8000 字**（按字符数计，中文 1 字 = 1 字符）。
- 运行时前端会把 `scriptTone` **全文**放进每回合 system 提示词，不截断；若平台对话接口对 system 消息有长度限制请告知。
- 旧字段 `gmIntro` / `worldIntro` / `narratorPersona` 仍是弃用兼容（前端读时并入 `scriptTone`），无变化。

## 3. 世界生成 `max_tokens` 与超时

接口：`POST /api/romance/world-gen/complete`，请求体字段 `max_tokens`。

| 生成内容 | 旧 `max_tokens` | 新 `max_tokens` |
|---|---|---|
| 单独生成系统提示词（模组 `prompt`） | 8000 | **12000** |
| 固定事件 / 剧情线（单模组） | 8000 | 8000（不变） |
| 系统提示词 + 线路大包 | 16000 | 16000（不变） |
| 其它多模组合并 | 12000 / 10000 / 8000 | 不变 |

- 前端超时：`60 秒 + max_tokens × 25 毫秒`，夹在 180–480 秒之间（12000 token ≈ 360 秒）。
- 后端需要：确认网关 / 模型侧放行 12000，且**接口超时 ≥ 前端超时**，否则会出现 408。封顶 16000 维持不变。
- 计费：系统提示词变长，单次生成消耗会上升，请确认计费按实际 token 计。

## 4. 人物线路解锁条件（跨周目）

字段：`content.creation.paths[]`

| 字段 | 类型 | 说明 |
|---|---|---|
| `lockConds` | `PathLockCond[]` | 解锁条件，全部满足才解锁；**种类已更换** |
| `lockHint` | `string?` | 前端根据条件自动生成的提示文案（如「通关任意结局一次（二周目）后解锁」） |
| `open` | `boolean?` | 作者手动开关，不变 |

`PathLockCond` 新定义（旧的 `stat` / `metric` / `rel` / `location` 已删除，前端读到会直接丢弃）：

```ts
type PathLockCond =
  | { kind: "clear" }                 // 通关过任意结局（二周目）
  | { kind: "ending"; key: string }   // 达成过指定结局，key = content.endings[].id
  | { kind: "route";  key: string }   // 用指定线路通关过，key = content.creation.paths[].id
  | { kind: "event";  key: string };  // 任意一局触发过指定事件，key = 固定事件 id
```

跨周目进度（判定解锁读这里）目前**只存在玩家本机 localStorage**：

```ts
// key：path-progress:<worldId>（作者预览为 preview-path-progress:<worldId>）
type PathProgress = { clears: number; endings: string[]; routes: string[]; events: string[] };
```

后端需要：
- 审核 / AI 生成校验里如有 `lockConds` 种类白名单，改为 `clear | ending | route | event`。
- ⚠ **建议新增**：按「用户 + 作品」云端保存 `PathProgress`，否则换设备或清缓存后二周目线路会重新上锁。建议接口（待后端定）：
  - `GET /api/romance/path-progress?worldId=` → `{ success, data: PathProgress }`
  - `POST /api/romance/path-progress` body `{ worldId, progress: PathProgress }`（前端合并后整体覆盖）
  - 后端确认后前端再接入，现阶段本机存储可正常使用。

## 10. 玩法 Mod（玩法包）

### 10.1 接口一览（前端当前调用）

⚠ **失败必须显式 `success: false`**：前端已改为「`success === false` 或 `ok === false` 一律判失败」，即使同时带了 `data`。此前 `{ success: false, data: {...} }` 会被误判为成功。请保证失败时不返回 `success: true`，也不要只靠 HTTP 状态码表达业务失败（适用于本节所有接口）。

| 用途 | 方法 & 路径 | 请求 | 前端读取的返回字段 |
|---|---|---|---|
| 上传玩法包 | `POST /api/components/kkmod/upload` | JSON：`{ filename, package, engineVersion, previewImages }`（见 10.2） | `success` / `ok`、`message`、`data.message`、组件 id（见下） |
| 提交审核 | `POST /api/components/kkmod/:modId/submit` | `{}` | `success`、`message`、`data.message` |
| 上传商店预览图 | `POST /api/auth/platform-apps/upload` | `multipart/form-data`，字段 `file` | `success`、`message`、`data.imageUrl` |
| 继续编辑（我的组件） | `GET /api/components/mine?kind=gameplay` | — | `data.items[]`：`id`、`slug`、`payload`、`previewImages[]` |
| 创作者身份门禁 | `GET /api/auth/games/user?limit=200` | — | `data[]`：`is_public`、`moderation_status` / `moderationStatus` |

⚠ **上传返回的组件 id**：前端依次从 `data.modId` → `data.id` → `data.componentId` → 顶层 `modId` / `id` / `componentId` 中取第一个非空字符串，用于随后提审。请后端**固定为 `data.modId`**，其余字段名可保留兼容但不要再新增别名。

### 10.2 上传请求体与 .kkmod 包结构

```jsonc

  "engineVersion": "1.0.0",          // 平台玩法 SDK 版本（PLAY_MOD_SDK_VERSION）

  "package": {
    "manifest": { /* 见下表 */ },
    "payload": {
      "mod": { /* 完整玩法 Mod，见下表 */ },

```

| `kind` | `"gameplay"` | 玩法包固定为 gameplay | — |
| `description` | string | ≤ 500 字 | — |
| `dependencies` | `Array<string \| { id, minVersion? }>` | 依赖的玩法 / 世界 id | 见 13.2 |
| `permissions` | string[] | 只会出现开放权限：`event.emit`、`settle.apply`、`ui.toast`、`save.game.read`、`save.game.write` 等 | — |

| `compatMax` | string? | 适配上限（目前不写） | — |

### 10.3 版本号

- 前端比较规则：按 `.` `+` `-` 拆分，比较前三段数字，缺省补 0（`cmpSemver` / `cmpVer`）。
- 本地模组校验要求 `^\d+\.\d+\.\d+([-+].*)?$`。
- ⚠ 请后端存储 / 比较版本时也按 `x.y.z` 处理；`compatMin` / `compatMax` 判定与前端一致：`SDK < compatMin` 或 `SDK > compatMax` 不可安装。

### 10.4 互斥（conflictsWith）与大小写

- 前端写入时：`trim` + 小写 + 过滤 `^[a-z0-9][a-z0-9_-]{1,48}$` + 去重 + 去掉自身 + 最多 20 个。
- 前端安装判定：**双向互斥**（A 声明与 B 互斥，或 B 声明与 A 互斥，都阻断）；slug、id、conflictsWith 全部**小写后比较**。
- ⚠ 此前前端比较区分大小写，slug 带大写时互斥失效。请后端若在服务端做安装校验 / 商店推荐过滤，也统一小写比较。

### 10.5 上传 → 提审流程

前端现在的规则：

1. 作者在对话里**每次保存**，都会作废上一次的上传记录，必须重新上传后才能提审（防止把旧版本送审）。
2. 「继续编辑」载入已有组件时，**不再允许不上传直接提审**。
3. 提审使用的 id = 最近一次上传成功返回的组件 id（无返回时回退到继续编辑的组件 id）。

⚠ 待后端确认：`/submit` 是否总是提交该组件**最新上传的版本**；若一个组件同时有「审核中」和「新上传的私有测试版」，提审 / 覆盖规则是什么。

### 10.6 商店预览图

- 张数：至少 1 张，最多 6 张，必须作者上传。
- 前端现在**逐张上传**，某一张失败时已成功的会保留；URL 去重。
- 预览图上传复用 `/api/auth/platform-apps/upload`（与手机应用同接口），返回 `data.imageUrl`。
- ⚠ 请确认该接口对玩法包预览图的格式 / 单张大小限制，前端目前只校验 `image/*`。
