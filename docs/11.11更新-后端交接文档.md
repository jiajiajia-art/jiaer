## 通用约定

1. **返回格式**：所有接口返回 `{ success: boolean; message?: string; code?: string; data: ... }`，失败时 `success=false` 并尽量带 `code`。
2. **作品与存档整体原样保存**：作品（模组 JSON / `mod.content`）、Romance 存档（`state`）、kkmod 包、地点库 `treeJson` 请**整体原样存储和返回，不做字段白名单过滤，也不按旧枚举校验或回改**。前端会持续新增字段，下文各处「⚠ 原样保存」都适用这一条，不再逐项要求。
3. **引用文档**：文中「另一份文档」均指 `Romance/docs/后端对接-字段与接口清单.md`，写明节号。

## 模块三：全站界面

> 纯前端改动，**不涉及接口和字段**。写在这里方便后端了解上线后的界面变化，以及以后如果要把主题偏好存到账号上该怎么接。

### 3.1 改动摘要

- 新增主题系统：一套变量名、多套取值；切换只改 `<html>` 上的 `data-theme`、`data-mode` 两个属性。
- 全站组件只读主题变量，不再写死颜色、渐变；浅色、深色和两套主题色（暗夜织梦、绯夜）在所有页面都生效，不会深浅混搭。
- 后台主色跟随主题；后台顶栏新增「皮肤」切换。
- 弹窗样式统一；修复浅色模式下多处「白字白底」「主色按钮深色字」等看不清的问题。

### 3.2 主题偏好存储（目前只存本地）

| 项 | 取值 | 存储位置 |
|---|---|---|
| 主题色 | `default`（暗夜织梦，珊瑚红）/ `crimson`（绯夜）；`ocean`、`amber` 已删除，读到旧值按 `default` 处理 | `localStorage['funloom.theme']` |
| 深浅模式 | `light` / `dark` / `system`，默认 `dark` | `localStorage['funloom.themeMode']` |

- 同一浏览器的多个标签页会自动同步；换设备或换浏览器不会同步。
- `index.html` 在页面加载前先读这两个值并写到 `<html>` 上，避免刷新时闪一下别的颜色。
- **可选的后续需求**：如果要让主题跟着账号走（多端同步），需要后端在用户信息里加一个偏好字段，例如 `uiPreferences: { theme, themeMode }`，登录后下发、修改时保存。前端只需在 `src/lib/theme.ts` 的 `setTheme` / `setThemeMode` 里多调一次保存接口。**本次不做**，见文末清单。

### 3.3 主题变量（前端约定，供参考）

  - `theme-base.css`：所有主题共用的中性色（底色、卡片、文字、边框、成功 / 危险色、阴影等），浅色写在 `[data-theme]` 上，深色写在 `[data-theme][data-mode="dark"]` 上。

## 模块五：AI 计费与运营仪表盘（可溯源）

运营后台「AI 模型中心 · 用量」（`src/components/ai-model-center/AiUsageDashboard.tsx`）的数据全部来自 `GET /operator/ai-model-center/usage` 与 `/usage/attempts`。本模块的总要求：**仪表盘上每一个数字、明细里每一个字段，都必须能查到它的来源**——来自哪条上游调用、哪条扣费 / 退款流水、哪个计价版本、哪个前端请求。

### 5.0 现状问题

**前端代码已确认：**

1. 仪表盘不会隐藏未关联作品的记录（显示「未关联作品」）。目前近 7 天一条都没有，说明接口没有返回创作调用。
2. 创作侧请求原来**不带作品、不带用途**：`POST /api/romance/world-gen/complete` 只发 `messages / engineId / moduleId / max_tokens / routeId`；`POST /api/romance/images/generate` 只发 `prompt / size / negativePrompt / referenceImages / routeId`。
3. 生成世界走的是按 `engineId` 扣积分的老方式（代码注释「运营 text-llm + 积分账本」），失败另调 `/world-gen/refund` 退积分。
4. `play/complete` 既用于玩家游玩，也用于编辑器里的对话；单看接口分不出是创作还是游玩。

**需后端确认（推断）：** `world-gen/complete`、`images/generate` 只写了老积分账本，没有写入仪表盘读取的计费调用表，因此创作成本、创作扣费都不在「平台总成本」「用户实际扣除」里。

### 5.1 前端已完成：扣费接口新增请求字段

涉及文件：`Romance/src/lib/aiTrace.ts`（新增）、`lib/platformPlayAi.ts`、`lib/platformWorldGenAi.ts`、`lib/platformImageGen.ts`、`lib/worldGenGenerate.ts`、`lib/ai.ts`、`components/OpeningStyleStudio.tsx`、`components/AiImageGen.tsx`。

适用接口：`POST /api/romance/play/complete`、`POST /api/romance/world-gen/complete`、`POST /api/romance/world-gen/refund`、`POST /api/romance/images/generate`。均为**新增可选字段**，原字段不变。

| 字段 | 类型 | 取值 | 前端怎么得到（来源） | 后端要求 |
|---|---|---|---|---|
| `scene` | string | `create_text` / `create_image` / `play_text` / `play_image` / `review_text` / `review_image` | 只看当前页面地址：`?play=1&fileId=` → `play_*`；`?reviewPreview=1&fileId=` → `review_*`；其余（创作页、编辑器、作者试玩）→ `create_*`。`_text` / `_image` 由接口类型决定 | 原样落库；**后端需用登录用户 + 作品归属复核**（如 `play_*` 但用户就是作者且作品未发布，应记录复核结果，不得静默改写） |
| `fileId` | string | 作品 / 草稿 id | `play_*` / `review_*` 取地址 `fileId`；`create_*` 取地址 `draftId`；没有则不传 | 落库；校验该 id 存在且当前用户有权访问，不通过时**保留原值并记 `fileIdVerified=false`**，不要丢弃 |
| `fileIdSource` | string | `url_play` / `url_review` / `url_draft` / `none` | 同上，标明 `fileId` 取自哪里 | 原样落库，用于核对 |
| `clientRequestId` | string | UUID | 前端每次调用生成一个 | 落库并建索引；同一 `clientRequestId` 的多次上游重试归为一组；**扣费幂等键** |
| `traceGroupId` | string | UUID | 世界生成：同一个模组这一次生成的骨架、补文、自动重试和退款共用一个 | 落库；退款请求按它在新计费里**定位要退的扣费流水**，由后端算应退金额（替代按客户端上报点数退款，见 5.2 第 3 条） |
| `feature` | string | 如 `world-gen:<模组id>`、`world-gen-refund:<模组id>`、`editor:opening-style`、`image:ai-image-gen`、`chat:stream`、`chat:complete` | 调用方写死的功能点 | 原样落库，便于定位到具体按钮 / 流程 |

前端不传这些字段时（旧客户端），后端按「未知」记录，不得报错。

### 5.2 后端要做：所有 AI 扣费统一迁移到新计费（已定）

**决定：所有 AI 调用的计价、扣费、退款统一走新计费逻辑（AI 模型中心的计价版本 + 计费调用记录），不保留两套并存。** 老的「按 `engineId` 扣积分」方式下线。

1. **统一入口**：`play/complete`、`world-gen/complete`、`world-gen/refund`、`images/generate`、TXT 文档解析，全部按新计费的计价版本计算成本和用户扣费，并写入计费调用记录（`usage/attempts` 的数据源），每次上游尝试一条。
2. **下线老逻辑**：去掉 `world-gen/complete` 按 `engineId` 固定扣分、`images/generate` 走老积分账本的扣费路径；`engineId` 字段前端暂时照发，仅作兼容，**不再参与计价**。
3. **退款也走新逻辑**：`world-gen/refund` 不再按前端上报的 `points` 退款，改为按 `traceGroupId` 找到这次任务在新计费里的扣费流水，由后端计算应退金额、幂等退款，退款流水指回原扣费流水。前端上报的 `points` 只作核对，不一致时以后端为准并记录差异。
4. **扣费流水可互查**：用户钱包流水（织梦豆 / KK 币）中每一笔 AI 扣费 / 退款必须带 `attemptId` 与 `clientRequestId`；计费调用记录反向带 `ledgerTxnIds`。
5. **响应保持兼容**：三个接口成功后仍返回 `pointsDeducted`、`remainingPoints`（前端用来更新顶栏余额、汇总退款），数值改为新计费的实际扣费结果。
6. **历史数据**：迁移上线前的老积分账本 AI 流水，导入为计费调用记录（标记 ⚠ `migratedFrom=legacy_points_ledger`，保留原流水 id），能补的字段照补、补不了的记 `null` 并标明，不得编造 token 或成本；导入后仪表盘历史区间才完整。
7. **切换与核对**：请提供上线时间点；上线后抽样核对一段时间（新计费扣费 = 用户钱包实际变动），核对结果写进本文。

### 5.3 溯源总原则（适用于下面每个字段）

- **来源可查**：每个字段写明来自哪里（前端请求 / 上游响应 / 计价版本 / 扣费流水 / 后端计算）。
- **计算可复算**：后端计算出来的数（成本、扣费）必须同时保存参与计算的原始值和所用计价版本，任何人拿明细能复算出同样结果。
- **不可篡改**：明细写入后只追加不修改；更正用新增「调整 / 退款」记录，并指向原记录。
- **可下钻**：概览、趋势、排行、聚合表里的每一个数字，都能点开看到组成它的调用明细列表（相同筛选条件），明细能看到对应的扣费 / 退款流水。
- **可关联**：一次用户操作 → `clientRequestId` → 若干上游尝试（`attemptId`）→ 扣费流水（`ledgerTxnId`）→ 退款流水（指回原流水），链路完整。

## 模块八：海外充值美元定价

> **一句话**：海外用户付美元。美元价格 = 人民币价格 × 一个倍率，倍率由运营在管理后台填写；买到的 KK币数量和国内一样。
>
> **当前状态**：前端已把「海外支付」按钮**隐藏**，用户看不到。后端把 8.2～8.4 做完、联调通过后，前端把 `RechargeModal.tsx` 里的 `OVERSEAS_PAY_ENABLED` 改成 `true` 就上线。
>
> 更细的说明（建表建议、上线步骤）在 `docs/海外充值倍率-后端接口文档.md`。

### 8.0 规则说明

**名词先对齐**

| 说法 | 意思 |
|---|---|
| 人民币价 | 国内的价格，例如 60 KK币档位是 ¥6。原有数据，不变。 |
| 倍率 | 1 元人民币要收多少美元。0.15 表示 ¥1 收 $0.15（大致是汇率，财务可以按手续费调高）。 |
| 默认倍率 | 全局一个倍率。没单独设置的档位、会员卡、自定义金额都用它。 |
| 档位倍率 | 某个档位单独设的倍率，填了就优先用它；不填（接口里是 `null`）就用默认倍率。 |

**算价格**

1. 美元价 = 人民币价 × 倍率。
2. 结果**往上**进到分（小数点后两位），保证不会少收钱。

| 档位 | 人民币价 | 倍率 | 计算 | 用户看到 |
|---|---|---|---|---|
| 60 KK币 | ¥6 | 0.15（默认） | 6 × 0.15 = 0.90 | $0.90 |
| 680 KK币 | ¥68 | 0.15（默认） | 68 × 0.15 = 10.20 | $10.20 |
| 1280 KK币 | ¥128 | 0.147（单独设置） | 128 × 0.147 = 18.816，往上进位 | $18.82 |

**其他规则**

- KK币数量不随币种变：海外买 60 KK币档位，照样到账 60（首充 66）。
- 会员卡（周卡 / 月卡）：人民币价 × 默认倍率。
- 自定义金额：用户直接输入美元。到账 KK币 = 美元 ÷ 默认倍率 × 10，**往下**取整（不多给）。例：输入 $1.00，倍率 0.15 → 1 ÷ 0.15 × 10 = 66.67 → 到账 66。不参与首充加赠。
- **钱以后端算的为准。**前端显示的价格只是给用户看的，后端下单时必须用同样的规则自己再算一遍，不能直接用前端传来的金额。
- 后端还没返回倍率时，前端暂时按 0.15 显示，防止页面空白。上线后请始终返回倍率。

### 8.2 后台设置倍率（新增 2 个接口，仅管理员可调）

运营在后台看到的样子：上面一个「默认倍率」输入框，下面是档位表（档位 / 人民币价 / 倍率 / 美元价），改倍率时美元价实时变化，点「保存倍率」提交。

#### 8.2.1 读取设置 `GET /admin/pay/overseas-pricing`

返回：

```json
{
  "success": true,
  "message": "ok",
  "data": {
    "currency": "USD",
    "defaultMultiplier": 0.15,
    "plans": [
      { "planId": "dr_6_v2",  "label": "60 KK币",  "cnyPrice": 6,  "multiplier": null },
      { "planId": "dr_30_v2", "label": "300 KK币", "cnyPrice": 30, "multiplier": 0.14 }
    ]
  }
}
```

| 字段 | 意思 |
|---|---|
| `defaultMultiplier` | 默认倍率 |
| `plans` | 所有在售的 KK币档位，按前台展示顺序排 |
| `plans[].cnyPrice` | 该档人民币价 |
| `plans[].multiplier` | 该档单独倍率；`null` = 没单独设，用默认倍率 |

#### 8.2.2 保存设置 `PUT /admin/pay/overseas-pricing`

前端提交的内容和 8.2.1 的 `data` 一样（不含 `currency`）。后端只需要读 `defaultMultiplier` 和每项的 `planId`、`multiplier`；`label`、`cnyPrice` 是前端顺带传的，**以数据库里的为准**，不要用它覆盖。

请检查以下情况，不通过就返回失败（`success: false` + `message` 写原因，前端会直接弹出 `message`）：

- 倍率必须是大于 0、不超过 10 的数字，最多 4 位小数。档位倍率允许 `null`。
- `planId` 必须是已存在的档位。
- 算出来的美元价不能低于支付渠道的最低金额（暂定 $0.50，以 EnjoyPayment 实际要求为准）。

保存成功：返回最新设置（格式同 8.2.1）。如果用户信息有缓存，要让它马上更新，否则用户还看到旧价格。建议记一条修改记录（谁、什么时候、改前改后）。

### 8.3 用户信息接口要多返回的字段（`auth.getUserInfo` 返回的 `user`）

充值弹窗靠这里的数据显示美元价。

```json
{
  "overseasPricing": { "currency": "USD", "rate": 0.15 },
  "kkRechargePlans": [
    { "id": "dr_30_v2", "price": 30, "baseDiamonds": 300, "firstBonusDiamonds": 30,
      "firstTotalDiamonds": 330, "firstChargeEligible": true, "label": "300 KK币",
      "overseasMultiplier": 0.14 }
  ]
}
```

| 字段 | 意思 |
|---|---|
| `overseasPricing.rate` | **就是默认倍率**，和 8.2 的 `defaultMultiplier` 是同一个值（这里沿用已有命名，叫 `rate`） |
| `kkRechargePlans[].overseasMultiplier`（新增） | 就是该档的单独倍率（8.2 里的 `multiplier`）。没单独设可以不返回，前端自动用默认倍率 |
| `kkRechargePlans[].price`（已有） | ⚠ 仍然是**人民币价**，不要改成美元，美元价由前端按倍率算 |

### 8.4 海外下单接口改造 `POST /pay/overseas/create`

前端传的参数不变（还是 `planId` 或 `amount`），后端按下表算出要收的美元：

| 用户买的是 | 前端传 | 后端收多少美元 |
|---|---|---|
| KK币固定档位 | `orderType: "diamonds"` + `planId` | 档位人民币价 × 档位倍率（没设用默认），往上进到分 |
| KK币自定义金额 | `orderType: "diamonds"` + `amount` | `amount` 本身就是美元。检查不低于最低金额、最多 2 位小数；到账 KK币按 8.0 计算 |
| 会员卡 | `orderType: "subscription"` + `planId` | 会员人民币价 × 默认倍率，往上进到分 |

还需要做：

1. 给 EnjoyPayment 下单时币种填 `USD`，金额填上面算出的美元。
2. **订单里把当时的价格信息存下来**：币种、美元金额（建议存成美分整数，例如 $4.20 存 420）、当时用的倍率、对应的人民币价。这样以后运营改了倍率，旧订单和对账也不会乱。
3. 收到支付成功通知时，核对通知里的金额和币种是否和订单里存的一致，**一致才发 KK币 / 会员**。
4. 接口返回里加上这几个字段：

| 字段 | 意思 | 例 |
|---|---|---|
| `currency` | 收款币种 | `"USD"` |
| `amount` | 实收美元 | `4.20` |
| `amountMinor` | 实收美分 | `420` |
| `multiplier` | 这单用的倍率 | `0.14` |

原来的 `amountYuan` / `amountFen` 前端已经不用了，可以先留着，之后再删。

### 9.2 云存档接口（新增 5 个，P1）

完整的 `SaveSlot` / `GameState` 字段沿用 `docs/后端对接-字段与接口清单.md` 第 2、3 节，这里只写约定和前端实际依赖的部分。

**通用规则**

- 鉴权：`Authorization: Bearer <token>`，存档只能被本人读写。
- 作品隔离：所有接口都带 `?gameFileId=`，同一用户不同作品的存档互不可见。
- 槽位：每个作品最多 6 个手动槽 + 1 个自动槽（`id = "autosave"`，`auto = true`）。
- 前端不会上传 `id` 以 `__author_preview` 开头的作者测试槽；如收到请直接拒绝。
- 前端遇到 HTTP 404 / 405 / 501 会视为「接口未上线」并停止本次会话的所有云存档请求。**上线后任何接口都不要返回这三个状态码**：槽位不存在请返回 HTTP 200 + `success: false` + `code: "SAVE_NOT_FOUND"`。

#### 9.2.1 存档列表 `GET /api/romance/saves?gameFileId=`

只返回摘要，**不要带 `state`**。

```json
{
  "success": true,
  "data": {
    "items": [
      { "id": "autosave", "name": "自动存档 · 林若雪", "auto": true, "updatedAt": 1736000000000,
        "summary": "第二周 · 山岚旅馆", "playerName": "林若雪", "playerAvatar": "https://…",
        "location": "山岚旅馆大堂", "time": "2024.03.15", "turnCount": 12, "ended": false }
    ]
  }
}
```

| 字段 | 必返 | 说明 |
|---|---|---|
| `id` / `name` / `updatedAt` | 是 | 前端靠 `updatedAt` 判断云端是否比本机新 |
| `auto` | 是 | 自动槽为 `true` |
| 其余字段 | 否 | 列表展示用，取自 `state`；`playerAvatar` 只给 URL，不要给 `data:` |

`data` 直接返回数组也兼容。

#### 9.2.2 读取存档 `GET /api/romance/saves/{slotId}?gameFileId=`

返回完整 `SaveSlot`：`{ id, name, updatedAt, auto?, state }`。不存在返回 HTTP 200 + `code: "SAVE_NOT_FOUND"`（不要用 404，见上）。

#### 9.2.3 写入存档 `PUT /api/romance/saves/{slotId}?gameFileId=`

body 为完整 `SaveSlot`，不存在则新建，存在则覆盖。

| 校验 | 失败返回 |
|---|---|
| 请求里的 `updatedAt` 早于库中记录 | 409 `code: "STALE_SAVE"`，**不得覆盖**（另一台设备已有更新的进度） |
| 新建手动槽时已有 6 个 | 409 `code: "SLOT_LIMIT"` |
| body 超过 10 MB | 413 `code: "SAVE_TOO_LARGE"` |

- 写入频率：手动存档立即上传；自动槽每 15 秒最多 1 次。请保证同一槽位的高频覆盖性能。
- 建议开启 gzip 请求体解压。
- 后端额外记录：`userId`、`gameFileId`、`createdAt`、`sizeBytes`、`schemaVersion`。
- `state` 请**整体原样存储**，不要按字段过滤（前端会持续新增存档字段）。

#### 9.2.4 重命名 `PATCH /api/romance/saves/{slotId}?gameFileId=`

body：`{ "name": "第一周 · 初入行" }`，只改名称，不改 `updatedAt` 以外的内容。名称为空返回失败。

#### 9.2.5 删除 `DELETE /api/romance/saves/{slotId}?gameFileId=`

删除后列表不再返回该槽。删除不存在的槽视为成功。

### 9.3 存档图片上传 `POST /api/romance/files`（新增，P2）

存档里的头像、立绘、CG、音频目前可能是 `data:`（内嵌 base64，存档体积大）或 `idb:`（仅本机有效，换设备打不开）。接口上线后，前端在上传存档前会先把它们换成 URL。

- 请求：`multipart/form-data`，字段 `file`、`kind`（`avatar` / `portrait` / `cg` / `audio`）
- 返回：`{ "success": true, "data": { "fileId": "…", "url": "https://…" } }`
- 请给出单文件大小上限与允许的格式，前端按此做前置校验。

### 9.4 验收标准

- [ ] 同一账号在设备 A 存档后，设备 B 打开同一作品的存档列表能看到并读取该进度
- [ ] 不同作品的存档互不可见；未登录、作者预览不产生云端数据
- [ ] 两台设备交替写同一槽位时，旧进度写入返回 409 `STALE_SAVE`，云端数据不被回退
- [ ] 第 7 个手动槽返回 409 `SLOT_LIMIT`；超 10 MB 返回 413 `SAVE_TOO_LARGE`
- [ ] 存档往返后 `state` 与上传内容一致（含 `gradeDims`、`attrDefs`、`endingGrade`、`modStamp`、`itemMemo` 等字段）
