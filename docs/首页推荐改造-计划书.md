# 首页「推荐」列表改造 — 最终可实施计划

> **范围锁定**：仅首页底部筛选栏「推荐」+ 下方游戏列表（`sort=recommended` → `GET /api/auth/games/public/no-discount`）。  
> **不改**：轮播、题材预览条、「最热 / 最新」、排行榜（除非共用服务层函数）。

**文档版本**：v1.1（千人千面）  
**最后更新**：2026-08-20

---

## 0. 目标与成功标准

| 目标 | 验收 |
|------|------|
| **千人千面** | 登录用户 A / B 在相同时间打开「推荐」，列表**明显不同**（同标签偏好驱动，抽样 ≥5 对账号） |
| **搜索优先画像** | 有最近 **2 条**搜索记录时：第 1 条标签权重 **80%**、第 2 条 **20%**，推荐同标签作品 |
| **行为兜底画像** | **无搜索**时：按用户游玩时长、点赞、转发所涉及作品的标签推送 |
| 新作品准入 | 无完整主角立绘 + NPC 生图的作品，**不进入「推荐」排序**（仍可在最热 / 最新 / 搜索出现） |
| 新作品冷启动 | 合格新作进入种子池，**推给 10–12 名匹配用户**（曝光计入） |
| 放量 | 种子期内按时长、点赞决定是否继续推给更多人 |
| 老作扶贫 | 低曝光合格老作，同样先推 10–12 人，再按时长决定是否放量 |
| 可配置 | 种子人数、天数、搜索权重、行为权重可后台或 env 调整，**不靠改 SQL 发版** |

## 2. 产品规则（定稿）

### 2.0 千人千面：个性化主链路（本次核心）

**一句话**：每个登录用户的「推荐」列表，优先用**最近 2 次搜索**导出的作品标签做召回；没有搜索时，改用**游玩时长 + 点赞 + 转发**所触达作品的标签。

```
登录用户打开首页「推荐」
  │
  ├─ 有 ≥1 条有效搜索记录？
  │     是 → 搜索画像路径（§2.0.1）
  │     否 → 行为画像路径（§2.0.2）
  │
  ├─ 未登录 / 双路径都无标签？
  │     → 热门质量分 + seeding 注入（§2.6.2）
  │
  └─ 混排：画像召回 + campaign 注入 + 质量兜底（§2.5）
```

#### 2.0.1 路径 A：最近 2 条搜索 → 标签推送（优先）

| 项 | 规则 |
|----|------|
| 取几条 | 该用户按时间倒序最近 **2** 条有效搜索（见下「有效」） |
| 权重 | **第 1 条（最新）权重 80%**；**第 2 条权重 20%** |
| 仅 1 条 | 第 1 条权重 **100%**（无第 2 条则不分 20%） |
| 0 条 | 走路径 B |

**什么叫「一条搜索」**：

- 用户在顶栏搜索框提交关键词（或点选搜索结果进入详情也算一次「意图」——**定稿：以服务端收到的搜索请求为准**，见 §6.4）
- 每次成功搜索写入 `user_search_history` 一行：`keyword`、可选命中的 `tag_ids`、时间

**从搜索得到「标签」**：

```
对第 i 次搜索 S_i：
  1) 若 keyword 精确命中某个 game_tag_categories.name / alias → 该 tag_id 直接入袋
  2) 否则取该次搜索结果 Top N（默认 N=10）作品的 game_tag_map 标签，按出现频次计分
  3) S_i 的标签向量 = 归一化后的 tag 权重（和为 1）

用户搜索画像：
  user_search_tag_weight[t] =
      0.80 × S_1.tag_weight[t]
    + 0.20 × S_2.tag_weight[t]     # 无 S_2 时第二项为 0，S_1 按 1.0 计
```

**用画像推作品**：

```
candidate_score(g) ∝ Σ_t  user_search_tag_weight[t] × I(t ∈ g.tags)
```

只推 `eligible=1` 且公开的作品；默认排除已玩 > `rank_played_exclude_seconds`（默认 300s）的作品。

**配置键**（写入 `recommend_config`）：

| 键 | 默认 | 说明 |
|----|------|------|
| `search_history_limit` | 2 | 参与画像的最近搜索条数 |
| `search_w_latest` | 0.80 | 最新一条搜索权重 |
| `search_w_prev` | 0.20 | 次新一条搜索权重 |
| `search_result_tag_top_n` | 10 | 关键词未直命中标签时，从结果取前 N 作标签统计 |
| `search_history_ttl_days` | 90 | 超过则不算「有效」搜索 |

#### 2.0.2 路径 B：无搜索 → 游玩 / 点赞 / 转发 → 标签推送

当用户 **0 条有效搜索**（或搜索标签向量全空）时启用。

**信号与权重（定稿，可配置）**：

```
behavior_tag_weight[t] =
    0.50 × norm( play_seconds_by_tag[t] )     # 近 90 天，对该标签下作品的累计游玩秒
  + 0.30 × norm( like_count_by_tag[t] )       # 该用户点赞作品所属标签计数
  + 0.20 × norm( share_count_by_tag[t] )      # game_share 事件所属作品标签计数
```

| 信号 | 数据源 | 说明 |
|------|--------|------|
| 游玩时长 | `user_analytics_events`：`game_session_duration` | `duration_seconds` 按 `game_file_id` → `game_tag_map` 分摊到标签 |
| 点赞 | `game_like`（`reaction` 为赞） | 按作品标签计入 |
| 转发 / 分享 | `user_analytics_events`：`event_type=game_share` | 按作品标签计入 |

**推送**：

```
candidate_score(g) ∝ Σ_t  behavior_tag_weight[t] × I(t ∈ g.tags)
```

取用户 **TopK 标签**（默认 K=5，写入 `user_recommend_profile.preferred_tag_ids`）做召回，避免全库扫。

**配置键**：

| 键 | 默认 | 说明 |
|----|------|------|
| `behavior_w_duration` | 0.50 | 时长权重 |
| `behavior_w_like` | 0.30 | 点赞权重 |
| `behavior_w_share` | 0.20 | 转发权重 |
| `behavior_lookback_days` | 90 | 行为统计窗口 |
| `behavior_top_k_tags` | 5 | 画像保留标签数 |

#### 2.0.3 与常规 `rank_score` 的衔接

登录用户最终排序（在 eligible 池内）：

```
rank_score(u, g) =
    0.70 × personal(u, g)     # 千人千面主信号：搜索 80/20 或行为标签
  + 0.20 × quality(g)         # 全站口碑（like / 时长 / 评分）
  + 0.10 × freshness(g)       # 轻度新作衰减
```

其中：

```
personal(u, g) =
  路径 A：基于 user_search_tag_weight 的 tag_match
  路径 B：基于 behavior_tag_weight 的 tag_match
```

**路径优先级不可混算**：有有效搜索时**只用路径 A 的 personal**，不用行为标签稀释搜索意图（行为仅在无搜索时启用）。Campaign 注入槽仍按 §2.5 叠加，不受路径切换影响。

#### 2.0.4 用户感知举例

| 用户 | 最近搜索 | 推荐偏向 |
|------|----------|----------|
| 甲 | ①「古风」②「宫斗」 | 约 80% 古风标签作 + 20% 宫斗标签作混排靠前 |
| 乙 | 仅 ①「赛博朋克」 | 几乎全是赛博相关标签作品 |
| 丙 | 无搜索；常玩恋爱向并点赞/转发 | 恋爱向标签作品靠前 |
| 丁 | 未登录 | 质量分 + seeding，与甲乙丙不同且全站近似一致 |

### 2.1 推荐准入（eligibility）

**主路径：发布时同步计算**（`POST /api/auth/games/publish` 成功落库后立即执行，不依赖定时任务）。

```
publish 成功
  → checkAndUpsertEligibility(fileId)   # 读 world / npcs，写 game_recommend_eligibility
  → eligible = 1 ?
       是 → 写入推荐池 + 创建 new_release campaign（若尚无）
       否 → 不写 campaign；首页「推荐」不可见，最热/最新/搜索不受影响
```

| 条件 | 规则 |
|------|------|
| 主角立绘 | `world.player.images.base` 非空且资源可读 |
| NPC 立绘 | 文档内**全部** NPC 均有 `images.base`（默认严格；可配置降级，见 §3.6） |
| 题材标签 | `game_tag_map` ≥ 1（发布流程已强制 1–2 个，与 publish 同一事务上下文校验） |
| 公开状态 | 本次 publish 已设 `is_public = 1` |
| TXT / 酒馆卡 | 无立绘要求；`eligible` 由 `txt_requires_portrait=0` 控制（默认可进推荐） |

**不合格**：发布仍可成功；仅 `sort=recommended` 查询中 `AND eligible = 1` 排除该作。

**补扫（非主路径，P4 或运维可选）**：

- 历史已发布作品：`POST /api/admin/recommend/eligibility/rescan` 批量回填
- 创作者在发布后继续补 NPC / 主角图：**再次 publish（更新上架）时重算**；日常 Cron 全量补扫仅作兜底，不是准入前置条件

### 2.2 新作品冷启动

| 项 | 规则 |
|----|------|
| 触发 | 首次 `is_public=1` 且 `eligible=1`，且尚无 `new_release` campaign |
| 种子人数 | `seed_users_min=10`，`seed_users_max=12`，默认目标 **11** |
| 选人 | 标签匹配（优先对上用户路径 A/B 画像）+ 未玩过 + 非作者；不足用同题材活跃用户补齐 |
| 曝光 | 用户打开首页「推荐」且该作出现在本页 → 记 1 次 seed 曝光（per user 去重） |
| 结束 | 曝光用户数 ≥ 目标 **或** 满 `seed_days`（默认 7 天） |

### 2.3 放量（时长 + 点赞）

种子期结束后计算得分（权重可配置）：

```
score = 0.5 × normalize(avg_duration_sec)
      + 0.3 × like_rate          # 点赞人数 / 有效游玩人数
      + 0.2 × engage_rate        # 游玩≥3分钟人数 / 曝光人数
```

| 结果 | 动作 |
|------|------|
| score ≥ `scale_hi` | `scaling`：每日推荐曝光上限倍增（11→22→44…，封顶可配） |
| `scale_lo` ≤ score < `scale_hi` | 维持种子流量，再观察 7 天 |
| score < `scale_lo` | `paused`：退出主动推荐加权，仅靠自然 like / PV |

#### 2.3.1 毕业（`graduated`）— 对用户怎么推荐

**含义**：扶持 campaign 结束，作品不再占用「种子 / 放量注入位」，进入**常规模型**排序，与同类老作同一套规则。

**触发条件**（同时满足，Cron 日检）：

| 条件 | 说明 |
|------|------|
| 当前状态 | `scaling` 且 `score ≥ scale_hi` 已连续维持，或 scaling 封顶后 |
| 自然流量稳定 | 连续 **`graduate_days=14`** 天：每日**非 campaign 注入**带来的 `game_entry` / 有效游玩 UV，波动 ≤ 配置阈值（默认：相对 7 日均值 ±40%） |
| 仍合格 | `eligible = 1` 且 `is_public = 1` |

**毕业后对用户侧行为**（首页「推荐」列表）：

```
graduated 作品
  ✗ 不再走 campaign 注入槽（§2.5 第 2 步）
  ✓ 仍可在 eligible 池内，参与：
      - 千人千面标签召回（§2.0）
      - 点赞 / 热度兜底补齐（§2.5 第 3 步）
  ✓ 排序分 = 常规模型（无额外 campaign 加权）
```

**用户感知**：不会看到「扶持中 / 新作位」等特殊标识；只是在「推荐」里按兴趣与口碑自然出现，位置取决于搜索/行为标签匹配与 `quality`，**不再保证每页固定露出**。

**与 `paused` 区别**：

| 状态 | 是否进推荐池 | 是否 campaign 注入 | 排序 |
|------|-------------|-------------------|------|
| `seeding` / `scaling` | 是 | **是**（优先注入 1–2 槽） | 注入 + 千人千面 + 兜底 |
| `graduated` | 是 | **否** | 仅千人千面 + 兜底（纯自然） |
| `paused` | 是（eligible） | 否 | 仅兜底，排序靠后，几乎无主动曝光 |

**状态流转简图**：

```
publish + eligible
    → seeding（10–12 人注入）
    → 种子期结束 → 算分
        → score ≥ scale_hi → scaling（注入 + daily_cap 递增）
        → scale_lo ≤ score < scale_hi → 再观察 7 天
        → score < scale_lo → paused
scaling + 14 天自然流量稳定 → graduated（停止注入，常规模型）
paused → 不自动复活；可 90 天后走 poverty_support 扶贫 campaign
```

### 2.4 老作扶贫

同时满足：

- `eligible = 1`
- `total_uv`（或 30 日游玩 UV）< `poverty_uv_max`（默认 50）
- 90 天内未做过 `poverty_support` campaign

流程同冷启动：10–12 人 → 按时长 / 点赞决定是否放量。

### 2.5 「推荐」列表混排（单页）

对当前用户生成一页（`limit` / `offset` 兼容现有分页）：

1. **千人千面召回**（登录）：路径 A 或 B 的标签加权候选
2. **注入槽位**：本页约 1–2 个 **`seeding` / `scaling`** 的 campaign 作品（未玩过）；**`graduated` / `paused` 不参与注入**
3. **补齐**：其余用点赞 / 热度兜底（列表不空）
4. **去重**：过滤不合格；默认排除已玩（游玩 > 5 分钟）

**按 campaign 状态对用户的影响**：

| 用户类型 | seeding / scaling | graduated | paused |
|----------|-------------------|-----------|--------|
| 标签匹配且未玩过 | 高概率出现在注入槽 | 按兴趣分排序，可能靠前 | 很少靠前，主要靠兜底 |
| 已玩过 | 不出现 | 不出现（去重） | 不出现 |
| 未登录 | 热门 + seeding 新作混排 | 与热作一起按 like / PV 排 | 基本看不到 |

未登录 / 新用户无画像：热门 + 正在 seeding 的新作混排。

### 2.6 常规模型（毕业后「正常竞争」机制）

**适用范围**：`graduated` 作品、从未进 campaign 的 eligible 老作、以及 `scaling` 注入槽之外的**补齐位**。  
**不适用**：`paused` 作品（见 §2.6.4）。

#### 2.6.1 单用户排序分（登录且有画像）

见 **§2.0.3**（`personal` 权重 0.70，主信号为搜索 80/20 或行为三信号）。

**① 个性化分 `personal(u, g)`** = `tag_match`（路径 A 或 B，互斥）

**② 质量分 `quality(g)`**（全站，与用户无关）

```
quality =
    0.40 × norm_log(like_count + 1)
  + 0.35 × norm(avg_duration_30d)     # 近 30 天人均有效游玩秒（≥3min 计）
  + 0.25 × norm(rating_avg × log(1 + rating_count))   # 评分 × 置信度
```

数据来源：`games.like_count`、`user_analytics_events` 聚合、`games.rating_*`。  
**推荐**：Cron 日写 `game_recommend_quality` 缓存表，列表查询不现场扫大表。

**③ 新鲜度分 `freshness(g)`**

```
freshness = exp( - days_since_publish / 60 )   # 约 60 天衰减到 0.37
```

#### 2.6.2 未登录 / 新用户（无画像）

```
rank_score = 0.70 × quality(g) + 0.30 × freshness(g)
```

不计算 `personal`。

#### 2.6.3 列表混排（与 §2.5 衔接）

单页 `limit=10` 生成顺序：

| 步骤 | 内容 | 数量 |
|------|------|------|
| 1 | `seeding` / `scaling` 注入（标签匹配、未玩过） | 1–2 |
| 2 | 常规模型 Top 召回（`rank_score` 降序，去重已玩） | 填满至 10 |
| 3 | 题材去重：同一一级标签最多 **3** 条/页 | 超出则换次高分 |
| 4 | 仍不足 | `quality` 全局 Top 补齐 |

**毕业后作品**只出现在步骤 2–4，**排名完全由 `rank_score` 决定**，无固定槽位。

#### 2.6.4 `paused` 与 `graduated` 在常规模型中的差异

| 状态 | 能否进步骤 2 召回 | 质量分 |
|------|------------------|--------|
| `graduated` / 无 campaign | 能 | 全额 `quality` |
| `paused` | **否**（仅步骤 4 兜底，且 `quality × 0.3`） | 强惩罚，几乎沉底 |

#### 2.6.5 配置项（追加）

| 键 | 默认 | 说明 |
|----|------|------|
| `rank_w_personal` | 0.70 | 千人千面个性化权重 |
| `rank_w_quality` | 0.20 | 质量权重 |
| `rank_w_freshness` | 0.10 | 新鲜度权重 |
| `rank_quality_w_like` | 0.40 | quality 内点赞占比 |
| `rank_quality_w_duration` | 0.35 | quality 内时长占比 |
| `rank_quality_w_rating` | 0.25 | quality 内评分占比 |
| `rank_freshness_half_life_days` | 60 | 新鲜度半衰期 |
| `rank_max_same_tag_per_page` | 3 | 同页同题材上限 |
| `rank_played_exclude_seconds` | 300 | 已玩超过此秒数则本页排除 |

#### 2.6.6 举例（用户甲：搜索「古风」80% +「宫斗」20%）

| 作品 | tag_match | quality | freshness | rank_score（约） |
|------|-----------|---------|-----------|------------------|
| 崇祯模拟器（古风） | 0.80 | 0.92 | 0.15 | **0.70×0.80 + 0.20×0.92 + 0.10×0.15 ≈ 0.76** |

## 8. 风险与对策

| 风险 | 对策 |
|------|------|
| 无搜索历史表导致路径 A 永远走不通 | P0 先上写入；上线后观察写入 UV |
| 关键词搜不到标签（生僻词） | TopN 结果标签频次兜底；再空则降级路径 B |
| 严格 NPC 全齐导致推荐池过少 | eligibility 看板；`npc_complete_mode` 可降级 |
| 种子有曝光无游玩 | 结算用 `engage_rate`；`daily_cap` 防刷 |
| D1 复杂 SQL 慢 | 预计算 profile / quality；列表只 JOIN 小表 |
| 与「最热」观感冲突 | 仅 `recommended` 走新逻辑 |
| 与现有 `/games/recommended` 重复 | 不新接 Home 第二套请求；逻辑合入 no-discount |
| 隐私 / 搜索词敏感 | 仅服务端存；管理端不默认展示明文；TTL + 条数上限 |
