# 运营者中心可视化报表 · 投稿数 — 计划书（v0.1）

> **文档类型**：产品 + 前后端联合计划  
> **日期**：2026-07-16  
> **页面**：`/operator/reports`  
> **关联**：`docs/operator-reports-spec.md`（v1 总规格）  
> **数据表**：`promotion_submissions`

---

## 1. 背景与现状

v1 已在「平台活跃」折线图中挂载 **投稿数** 曲线：

| 项 | 现状 |
|----|------|
| API | `GET /api/operator/reports/activity-trends`，metric key = `submission` |
| 口径 | `COUNT(*)` from `promotion_submissions`，按 `submitted_at` → 上海日分桶 |
| 状态 | **不过滤** `review_status`（待审 / 通过 / 驳回全算） |
| 前端 | 与 PV / 评论 / 分享 **同轴四线**；无投稿 KPI 卡片；无活动筛选 |

**核心问题**：

1. **可读性差**：PV 量级远大于投稿，投稿线在主图上接近贴底，运营难读。
2. **决策信息不足**：只有「提交次数」，看不到通过率、待审积压、驳回占比。
3. **活动维度缺失**：多活动并行时无法按活动拆开看。
4. **与拉新页重叠不清**：拉新 overview 的「推广投稿数」与报表「投稿数」同表同口径，但页面文案/入口分散，易误解为「有效邀请」。

---

## 2. 目标

在运营报表里让「投稿数」**可独立阅读、可解释、可下钻**，服务两类问题：

- 推广活动是否在涨？（量）
- 审核是否跟得上、质量是否健康？（结构）

**非目标（本计划不做）**：

- 改投稿审核工作流 / 奖励发放逻辑
- 把投稿与邀请码绑定成漏斗（可另开「拉新漏斗」计划）
- 导出 CSV / 定时邮件（可 P3 再议）

---

## 3. 已锁定口径（建议拍板）

| 项 | 口径 | 备注 |
|----|------|------|
| **投稿数（总量）** | `promotion_submissions` 按 `submitted_at` 计入；含全部 `review_status` | 与 v1 / 拉新 overview 一致，**不改历史语义** |
| **待审 / 通过 / 驳回** | 按 **当前** `review_status` 分组计数；时间仍用 `submitted_at` | 不用 `reviewed_at` 做主趋势（避免「今天审了上周稿」扭曲日投稿曲线） |
| **通过率** | 区间内 `approved / (approved + rejected)`；分母不含 `pending_review` | Tip 写清：待审不进通过率 |
| **去重投稿用户** | 区间内 `COUNT(DISTINCT user_id)` | 反映参与广度，非次数 |
| **时区 / 粒度 / 缺日补 0** | 沿用 `operator-reports-spec`：上海日、日/周/月、补 0 | |
| **文案** | 统一叫「推广投稿数」；Tip：≠ 邀请数、含全状态 | 与拉新页 tip 对齐 |

`review_status` 枚举（现网）：`pending_review` | `approved` | `rejected`（以代码为准，实现前再扫一遍写入点）。

## 4. 方案分层

### P0 — 展示可读（不改口径，改前端为主）

**目的**：立刻能看清投稿趋势。

| 改动 | 说明 |
|------|------|
| 指标开关 | 活跃图可勾选投稿 / PV / 评论 / 分享；默认勾选投稿+评论+分享，PV 可选 |
| 或双 Y 轴 | 左轴次数小指标、右轴 PV（二选一，优先「开关」更简单） |
| KPI 卡片 | 统计期内：投稿总数、日均、峰值日；放在活跃图上方或侧栏 |
| Tip | 投稿卡片/图例挂 tip，复用拉新文案 |

**验收**：近 30 天仅勾选投稿时，曲线波动清晰可见。

### P1 — 投稿专项区块（后端 + 前端）

**目的**：量 + 结构一眼看完。

#### 4.1 新 API（建议）

```
GET /api/operator/reports/submissions/summary
  ?startDate&endDate
  → {
      total,                 // 全状态投稿数
      uniqueUsers,           // 去重用户
      byStatus: { pending_review, approved, rejected },
      approvalRate,          // approved/(approved+rejected)，无审结则为 null
      dailyAvg, peakDay, peakValue
    }

GET /api/operator/reports/submissions/trend
  ?granularity&startDate&endDate&activityId?
  → {
      series: [
        { key: 'submission', label: '投稿数', points },
        { key: 'approved', ... },      // 可选：按状态拆线
        { key: 'rejected', ... },
        { key: 'pending_review', ... }
      ]
    }
```

也可扩展现有 `activity-trends` 的 `metrics`，但 **独立 path 更清晰**，避免与 PV 同响应耦合。

#### 4.2 前端

在 `/operator/reports` 增加一节 **「推广投稿」**（在平台活跃图下方或独立 Tab）：

1. KPI 行：总数 / 去重用户 / 待审 / 通过率  
2. 折线或堆叠柱：全量趋势；可选「按状态拆分」  
3. 沿用页顶日期 + 粒度筛选  

#### 4.3 实现落点

| 层 | 文件（预期） |
|----|----------------|
| BE 查询 | `services/d1/operatorReportsService.js`（或拆 `reports/submissionReports.js`） |
| BE 路由 | `interface/handlers/operator/reports.js` + `operatorRoutes.js` |
| FE API | `src/api/stats/operatorReportsApi.ts` |
| FE 页 | `src/page/operator/OperatorReports.tsx` |
| 单测 | 前后端 `checks/operatorReports*.check.mjs` 增投稿用例 |

**验收**：改日期后 KPI 与趋势一致；人工抽样 SQL 与接口误差为 0。

### P2 — 按活动下钻

| 改动 | 说明 |
|------|------|
| 筛选 | `activityId` 下拉（来自 `promotion_activities` 已发布/全部） |
| Top 表 | 区间内各活动投稿数、通过数、通过率、待审数（限 Top N） |
| 权限 | 仍 `requireOperatorUser` |

**验收**：选单活动后，趋势与 KPI 只含该活动。

### P3（可选，本计划不排期）

- 按 `reviewed_at` 的「审核产出」曲线（审稿产能）  
- 导出 CSV  
- 与邀请码漏斗对齐的转化看板

## 5. 与现有模块关系

```
拉新 overview（promotionSubmissions）
        │  同表、同「全状态 COUNT」
        ▼
报表 v1 activity-trends.submission  ──P0──► 可读性增强（开关/KPI）
        │
        └──P1/P2──► 投稿专项 summary + trend + 活动下钻
```

- **不删** v1 活跃图上的投稿线；P0 用开关解决抢戏。  
- 拉新页数字与报表 KPI **必须同口径**；若以后要「仅已通过」，单独加 metric，禁止静默改 `submission` 语义。

## 6. 风险与注意

| 风险 | 处理 |
|------|------|
| 表不存在 / 空库 | 已有 `tableExists` 兜底，返回空序列 + 0 |
| 状态枚举新增 | 单测锁死已知状态；未知状态计入 `total` 并打 log，不进通过率分母 |
| 性能 | 已有 `idx_promotion_submissions_submitted_at`；活动筛选走 `activity_id` 索引 |
| PV 与投稿同图误读 | P0 默认弱化 PV 或拆轴，文案标明「次数」 |

## 7. 建议排期

| 阶段 | 预估 | 交付物 |
|------|------|--------|
| P0 | 0.5～1 天 | 指标开关 + 投稿 KPI + tip |
| P1 | 1～1.5 天 | summary/trend API + 专项区块 + 单测 |
| P2 | 1 天 | 活动筛选 + Top 表 |
