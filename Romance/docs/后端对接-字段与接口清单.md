# Romance · 后端对接：字段与接口清单

给后端对字段用。字段名、类型都以前端代码为准（`Romance/src/lib/types.ts`、`src/game/logic.ts`、`src/game/phone.ts`、`src/lib/storage.ts`）。前端改了类型，这份文档也要跟着改。

约定：

- 鉴权：`Authorization: Bearer <token>`，token 取自前端 `localStorage["auth-storage"].state.user.token`。
- 基址：`resolveFunloomApiBase()`，可以为空（同源反代时就是 `/api/...`）。
- 统一返回：`{ success: boolean, data?: T, message?: string, code?: string }`。未登录返回 HTTP 401 + `code: "NOT_LOGGED_IN"`；积分不足建议 HTTP 402 + `code: "INSUFFICIENT_POINTS"`。
- 时间戳一律用**毫秒**数字（前端 `Date.now()`）。游戏内日期是字符串 `YYYY.MM.DD`。
- 所有 id 都是前端生成的字符串，后端**原样保存**，不要改写。

## 2. 云存档接口（新做）

前端的存档单位是**存档槽**（`SaveSlot`）。每个作品（`worldId`/作品 fileId）下，一个用户最多 6 个手动槽 + 1 个自动槽。

### 2.1 SaveSlot

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `id` | string | 是 | 槽位 id。自动槽固定为 `"autosave"`，手动槽由前端生成 |
| `name` | string | 是 | 显示名，可以重命名 |
| `updatedAt` | number | 是 | 最近写入时间（毫秒） |
| `auto` | boolean | 否 | 是否自动槽 |
| `state` | GameState | 是 | 完整游戏状态，见第 3 节。**体积大**（常见几百 KB，长局可能几 MB） |

后端额外保存的列（不在 state 里）：`userId`、`gameFileId`、`createdAt`、`sizeBytes`、`schemaVersion`。

以 `id` 开头为 `__author_preview` 的槽是作者预览用的，**不要**上传，也不要出现在列表里。

### 2.2 接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/romance/saves?gameFileId=` | 列表。**只返回摘要，不带 `state`** |
| GET | `/api/romance/saves/{slotId}?gameFileId=` | 读一个槽，返回完整 `SaveSlot` |
| PUT | `/api/romance/saves/{slotId}?gameFileId=` | 新建或覆盖。body = `SaveSlot` |
| PATCH | `/api/romance/saves/{slotId}?gameFileId=` | 只改 `name` |
| DELETE | `/api/romance/saves/{slotId}?gameFileId=` | 删除 |

列表项（摘要）字段：

```json
{
  "id": "autosave",
  "name": "自动存档",
  "auto": true,
  "updatedAt": 1736000000000,
  "summary": "state.saveSummary",
  "playerName": "state.player.name",
  "playerAvatar": "state.player.avatar（只给 URL，不要给 data:）",
  "location": "state.world.location",
  "time": "state.world.time",
  "turnCount": 12,
  "ended": false
}
```

写入规则：

- 前端自动存档有 300ms 防抖，但仍然会频繁写，**PUT 要能承受高频覆盖**。建议后端按 `updatedAt` 做乐观并发：请求里的 `updatedAt` 比库里的旧就返回 409 `code: "STALE_SAVE"`。
- 手动槽超过 6 个返回 409 `code: "SLOT_LIMIT"`。
- body 建议开 gzip；单槽上限建议 10 MB，超出返回 413 `code: "SAVE_TOO_LARGE"`。

## 3. GameState 字段（存档本体）

后端**不需要解析**整个 `state`，按 JSON 原样存取即可。下表列出后端会**读**或需要**特殊处理**的字段，其余字段原样保存。

### 3.1 顶层

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | string | 存档 saveId。私有数据 key 的前缀 |
| `worldId` | string | 世界观 id（老存档缺省 `"ent"`） |
| `player` | Player | 主角，见 3.2 |
| `npcs` | Npc[] | 人物，见 3.3 |
| `story` | Turn[] | 主线剧情回合，见 3.4 |
| `world` | `{ time, location, weather, note? }` | 当前时间地点天气 |
| `memory` | string | 压缩后的主线记忆。**只给 AI 看**，里面会夹带连贯性备注（如"本应…""未核对…"），后端若要做摘要展示 / 分享卡片，**不要直接用它**，请用 `journal`（见 3.7） |
| `turnCount` | number | 回合数 |
| `ended` | boolean | 是否已结局 |
| `saveSummary` | string? | 存档摘要，列表展示用 |
| `sim` | SimState | 数值引擎（周、天、属性、金钱、日程……），见 3.5 |
| `phone` | PhoneState? | 手机数据，见 3.6 |
| `privateData` | `Record<string, string>`? | 存档私有数据快照，value 本身是 JSON 字符串，**不要二次解析** |
| `createdAt` / `updatedAt` | number | 毫秒 |
| `ending*` | string? | 结局相关（`endingTitle`、`endingKind` 等），结局页展示用 |
| `journal` | JournalEntry[]? | 剧情志：玩家亲历过的单篇剧情，剧情志「前情提要 / 回顾」的数据源，见 3.7 |
| `timeLimit` / `gradeDims` / `attrDefs` / `endingGrade` | 见第 15 节 | 结算时限与结局评级，开局从作品物化进存档 |

其他字段（`worldBook`、`mapEdits`、`fixedEvents`、`customEndings`、`cgs`、`audio`、`relNet`、`diaries`……）都是前端玩法数据，原样保存即可。

|------|------|------|

| `age` | string | **字符串**，不是数字 |
| `gender` / `identity` / `background` / `klass` / `description` | string | 基础资料 |
| `avatar` | string | URL 或 `data:` 图片，见第 4 节 |
| `attrs` | `{ key, label, value, max, icon? }[]` | 属性 |
| `history` | `{ turn, time, title, detail }[]` | 经历 |
| `extra` | `{ label, value }[]` | 自定义扩展字段 |

### 3.3 Npc

| 字段 | 类型 | 说明 |
|------|------|------|

| `name` | string | 档案全名（姓+名） |
| `aliases` | string[]? | 别名，剧情里按别名匹配到同一个人 |
| `age` | string | 字符串 |
| `identity` / `relation` / `bio` / `mood` | string | 资料 |
| `avatar` / `portrait` | string | 头像 / 立绘，见第 4 节 |
| `affinity` | number | 总好感，-100 ~ 100 |
| `dims` | `{ label, value }[]` | 好感维度（信任、爱慕……） |

| `persona` | object? | 玩家自定义人设（性别、口吻、规则、示例对话） |
| `edited` | string[]? | 玩家改过的字段：`name`/`age`/`identity`/`relation`/`bio` |

### 3.4 Turn（剧情回合）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | string | 回合 id |
| `role` | `"player"` \| `"ai"` | 谁说的 |
| `segments` | Segment[] | 正文分段 |
| `ts` | number | 毫秒 |
| `scene` | string? | 本回合转场到的地点名 |
| `raw` | string? | AI 原文（可选，体积大时后端可不存） |
| `error` | `{ title, text }`? | 请求失败提示，**不计入剧情** |
| `thoughts` | `{ name, text }[]`? | 角色心事 |
| `newcomers` | string[]? | 本回合初遇的人物 id |

Segment 是联合类型，用 `kind` 区分：

```ts
{ kind: "narration"; text: string }
{ kind: "dialogue"; speaker: string; text: string } // speaker 是名字或别名，不是 id
{ kind: "system"; text: string }
```

### 3.5 SimState（`state.sim`，数值引擎）

后端一般不用读。如果要做排行榜 / 运营统计，常用字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `week` / `day` | number | 生涯第几周 / 第几天（0 起） |
| `money` | number | 资金（元） |
| `fame` / `reputation` / `stress` / `energy` | number | 名气 / 口碑（0-100）/ 压力（0-100）/ 行动力（0-100） |
| `works` / `awards` | number | 作品数 / 奖项数 |
| `stats` | `Record<string, number>` | 八维属性 |
| `cattrs` | `Record<string, number>`? | 自定义属性当前值（key = AttrDef.id） |
| `ap` | number? | 当前行动点；缺省视为满值（`travel.apPerTurn`，默认 10）。每次「推进」回满；换地点、地点行动、进入支线、**剧情行动、当面对话**都会扣（见 5.4 `travel.apPerAct` / `apPerTalk`） |
| `mobs` | `Record<string, string>`? | NPC 实时位置：人物 id → 地点（room）id。**现在每个剧情回合都会变化**（原先只在玩家换地点时变） |
| `tick` | number? | 世界心跳计数；每个剧情回合 +1、换地点 +1 |
| `rel` | `Record<personId, number>` | **好感**（人物关系主轴）。范围 **-100 ~ 上限**（上限默认 100），**允许负数**，后端若有校验请勿按 ≥0 截断 |
| `relations` | `Record<personId, { romantic, trust, mood, ... }>` | 关系细项。`romantic` = **爱慕**，范围 0 ~ 该人物爱慕上限（默认 100），**不允许负数**；`trust` / `mood` 按前端 `RELATIONS` 配置的上下限 |
| `noRomance` | string[]? | 玩家在人物页关掉「可攻略」的人物 id。缺省 = 人人可攻略；关闭后爱慕冻结 |

> 展示口径（线下见面 / 人物页）：好感在上、爱慕在下；好感条为双向（0 居中，负值向左）。普通 NPC 没有八维能力数值时不展示「个人能力」，后端无需为 NPC 补默认能力值。

> 玩法数值绑定：作品若在 `mod.content.metricBind` 里把名气 / 口碑 / 黑粉 / 体能绑定到建角属性，前端每次落盘会把 `fame` / `reputation` / `blackFans` / `stats.tineng` 与对应的 `cattrs[属性id]` 双向同步（按属性上下限截断）。所以做排行榜时 `fame` 与绑定属性的值一致，口径不变；但量级跟随作者属性（例如 0–100），不再固定 0–1000。

### 3.6 PhoneState（`state.phone`）

| 字段 | 类型 | 说明 |
|------|------|------|
| `contacts` | string[] | 好友的 personId |
| `pending` | string[]? | 已发好友申请、对方未处理 |
| `threads` | Thread[] | 聊天会话 |
| `calls` | CallRecord[] | 通话记录 |
| `follows` / `likes` / `saves` | string[] | 关注 / 点赞 / 收藏的 id |
| `comments` | `Record<内容id, UserComment[]>` | 玩家评论 |
| `posts` | `Record<appKey, UserPost[]>` | 玩家发布的内容（key 如 `weibo`、`moments`） |
| `tickets` | HeldTicket[] | 已购票 |
| `mails` | Mail[]? | 邮件 |
| `acts` / `npcNet` | 数组? | 线上线下联动流水 |
| `seenMoments` | number | 朋友圈已读游标 |
| `msgPref` | `Record<personId, "active" \| "quiet" \| "block">`? | 玩家逐人设的消息权限：主动联系 / 不主动发 / 禁止发消息；缺省（不在表里）= 随剧情。原样保存即可 |

手机里的时间有两种：`ts` 是现实毫秒时间，`gt` 是游戏内时间，**不要混用**。

### 3.7 JournalEntry（`state.journal[]`，剧情志）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `id` | string | 是 | 条目 id |
| `kind` | `"spot"` \| `"quest"` \| `"note"` | 是 | 点位事件 / 支线剧情 / 地点备注 |
| `srcId` | string | 否 | 来源事件 / 支线 id，用于一次性事件去重 |
| `title` | string | 是 | 标题，前情提要直接展示 |
| `annotation` | string | 否 | 备注 |
| `seed` | string | 是 | 触发种子文案（`text` 缺省时展示它） |
| `text` | string | 否 | AI 演绎正文，体积可能较大 |
| `location` | string | 否 | 触发时地点名 |
| `when` | string | 否 | 触发时游戏内时间（如「第 1 周 · 周六」），**不是**时间戳 |
| `ts` | number | 是 | 现实毫秒时间 |
| `fav` | boolean | 否 | 是否收藏 |

前情提要规则：有 `journal` 时按顺序取 `title` + `when · location`；没有时才退回 `memory`，并由前端过滤掉 AI 备注句。

## 4. 图片和音频：要先上传成 URL

现在头像、立绘、CG、音频有三种写法：`https://...` URL、`data:` 内嵌 base64、`idb:<key>`（只在本机有效）。

上云之前要统一成 URL，否则存档会非常大，换设备后 `idb:` 也打不开。需要后端提供：

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/romance/files` | `multipart/form-data`，字段 `file` + `kind`（`avatar` / `portrait` / `cg` / `audio`）。返回 `{ fileId, url }` |

前端在上传存档前，会把 `data:` 和 `idb:` 替换成返回的 `url`。CG 新数据已经用 `imageFileId` 字段，对应这里的 `fileId`。

## 5. 已有接口字段（核对用）

### 5.1 剧情演绎 `POST /api/romance/play/complete`

> **调用量变化（请评估计费 / 限流）**：玩家在地图上**进入一个地点**时，前端现在会自动发起一次剧情演绎请求（由 AI 写进入场景的剧情）。原先进入地点不调用 AI。即每次换地点多 1 次请求、多扣一次积分。若后端对单用户有频率限制，请确认能覆盖「连续换地点」的场景；如需要，可在请求里区分来源（前端可加 `scene: "arrival"` 字段，请告知是否需要）。

请求：

```json
{ "messages": [{ "role": "system|user|assistant", "content": "..." }], "max_tokens": 4000 }
```

返回 `data`：`{ "text": "...", "pointsDeducted": 3, "remainingPoints": 120 }`

### 5.2 生成世界 `POST /api/romance/world-gen/complete`

请求：`{ messages, engineId: "balanced", moduleId, max_tokens }`，返回同 5.1。

**超时（P0）**：前端单次等待 = `60s + max_tokens × 25ms`，最短 180s、最长 480s。**请把该接口在服务端 / 网关 / 反向代理（Nginx、SLB、函数计算等）的超时调到 ≥ 480 秒**，否则前端还在等、服务端已断开，表现为 502/504 或空响应。前端超时后最多重试 1 次；客户端断开后若服务端仍计费，需要配合下方返还。

**`moduleId` 与 `max_tokens`**（核心流程固定三次串行请求）：

| 顺序 | 批次 | `moduleId` | `max_tokens` |
|---|---|---|---|
| 1 | 基础设定（剧本基调 / 规则 / 世界书 / 开局时间与资金 / 建角 / 人物线路） | `phase1Foundation` | 16000 |
| 2 | 人物与地点 | `phase2WorldCast` | 10000 |
| 3 | 事件与剧情线（**新增**，从原第 2 次拆出） | `phase3StoryArc` | 10000 |
| 4+ | 扩展批：`contacts` / `opening` / `avatars` / `training` / `playMods` / `beautify` / `solo:<模块id>` | 同名 | 4000–12000 |

- 请确认 `max_tokens` 上限 ≥ 16000；超过上限请截断而不是拒绝。
- 若后端按 `moduleId` 做计费、白名单、统计或限流，请加入 `phase3StoryArc`，规则同 `phase2WorldCast`。

退积分 `POST /api/romance/world-gen/refund`：`{ engineId, moduleId, points, reason: "module_failed_after_charge" }`，返回 `{ success }`。
- 触发时机：已扣费但前端解析 / 校验失败（含重试后仍失败）。
- 需接受 `moduleId = phase3StoryArc`；同一请求重复返还须幂等（建议 `moduleId + 请求 id` 去重）。

### 5.3 生图 `POST /api/romance/images/generate`

请求：`{ prompt, size?, negativePrompt?, referenceImages?: string[] }`。

**负面词需要确认（P1）**：前端目前把负面词**发了两份**——

1. 单独字段 `negativePrompt`：`"文字，水印，UI 边框，多余肢体，畸形手指"` 这类逗号分隔的中文短语；
2. 同时追加在 `prompt` 末尾：`"<正向描述>\n\n【负面词·避免出现】文字，水印……"`。

这么做是因为不确定后端是否使用 `negativePrompt`。问题是：如果底层模型不理解这段标注，写在 `prompt` 里的「文字、水印」反而可能被画出来。请后端确认：

- 后端是否把 `negativePrompt` 传给了底层生图模型（或按模型能力转成对应参数）？
- 若**已使用**：告知后前端会去掉 `prompt` 末尾那段，只发单独字段。
- 若**未使用**：请接入；或说明底层模型只接受单条 prompt，前端保持现状。

`size` 取值：人物头像 `1024x1024`；地点场景 / 大地图 / 作品封面为 9:16 竖图（`SCENE_PORTRAIT_GEN_SIZE`）。

### 5.4 作品草稿

- `PATCH /api/auth/games/drafts/romance/{fileId}`：`{ title, cover_url? }`。title 最多 80 字，空的就填「未命名 Romance 作品」。
- `PUT / GET .../{fileId}/content`：

```json
{ "version": 1, "s1": {}, "draft": {}, "mod": {}, "updatedAt": 1736000000000 }
```

`mod` 和 `draft` 缺一个，前端就当作不能续编。

**`mod.content` 新增 / 放宽的可选字段**（若后端对 `content` 做白名单、Schema 校验或字段裁剪，请放行；整体存取 JSON 则无需改动）：

| 字段路径 | 类型 | 说明 |
|---|---|---|
| `metricBind` | `{ fame?, reputation?, blackFans?, stamina?: string }` | 玩法数值绑定，值为 `customAttrs[].id`（见 3.5） |
| `meals[].cgain` | `Record<string, number>` | 伙食对建角属性的每周变化，键为 `customAttrs[].id` |
| `gigs[].statReq` / `gigs[].grow` | `Record<string, number>` | 键可以是建角属性 id（原来只能是内置八维） |

## 8. 平台素材库与 Mod 字段对齐（新增）

### 8.1 图片地址口径（P0，当前线上问题）

**现象**：手机桌面里「冲浪 / 小粉书 / 票团团 / 云音乐 / 老板直聘」等平台应用显示成空白方块，后台明明配了图标。

**要求**（适用于所有图片字段：`icon`、`previews[]`、头像 `imageUrl / thumbUrl / originalUrl`、地点素材图）：

4. 删除或替换图片后旧 URL 尽量保留一段时间，或接口同步返回新地址。

- 验收：直接在浏览器打开接口返回的 `icon` 值能看到图片；手机桌面图标正常显示。

## 15. 结算时限与结局评级维度（字段对齐）

前端已改：结算时限与主线完成条件分开说明；结局评级不再用「可爱度 / 美丽度 / 成长度 / 故事完成度」内置兜底，改为按本作品建角属性打分。**不需要新接口**，只涉及作品正文（`mod.content`）与存档 `state` 里的字段，后端原样存取即可；如有字段校验请按下表放行。

### 15.1 两套机制，不是重复字段

| | 结算时限 `timeLimit` | 主线节点完成条件 `storylines[].nodes[].conds` |
|---|---|---|
| 管什么 | 本局**日历天数**到上限 → 强制结算 | 节点的数值 / 事件条件满足 → 节点完成 |
| 不设时 | 不因天数强制结算 | 该节点不会自动完成 |
| 位置 | 作品 `content.timeLimit` → 开局写入 `state.timeLimit` | 作品 `content.storylines` |

后端/运营文案请统一叫「本局时限」或「结算时限」，**不要叫「主线时限」**。

### 15.2 TimeLimit（`content.timeLimit` / `state.timeLimit`，可缺省）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `value` | number | 是 | 时长数值 |
| `unit` | `"year" \| "month" \| "week" \| "day"` | 是 | 单位 |
| `endDate` | string | 否 | 固定截止日期 `YYYY.MM.DD`，设置后优先按与开局日期之差算总天数 |

缺省（字段不存在）= 不限时。

### 15.3 GradeDim（`content.gradeDims` / `state.gradeDims`，数组，最多 4 条）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | 前端生成；自动生成的维度形如 `dim_auto_<属性id>` |
| `label` | string | 是 | 显示名，≤ 8 字 |
| `icon` | `"heart" \| "star" \| "leaf" \| "book" \| "crown" \| "note"` | 是 | 图标 |
| `src` | `{ kind: "stat" \| "metric", key: string }` | 是 | 取值来源；自定义属性为 `kind:"metric", key:"c:<属性id>"` |
| `full` | number | 是 | 满分值（> 0） |
| `lower` | boolean | 否 | 越低越好 |

规则：

- 作品里**不设** `gradeDims` 时，开局由前端按建角属性 `content.customAttrs`（前 4 条，满分取属性 `max`，缺省 100）生成并写入 `state.gradeDims`。后端**不要**自行补默认值，更不要补可爱度等四项。
- 作品既无 `gradeDims` 也无建角属性时，`state.gradeDims` 不存在，属正常情况。
- 后端若有 schema 校验：`gradeDims` 长度 0~4；空数组与缺省等价（前端保存时空数组会写成缺省）。

### 15.4 相关存档字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `state.attrDefs` | AttrDef[]? | 本局建角属性定义（开局从 `customAttrs` 拷贝），自动维度的来源 |
| `state.sim.cattrs` | `Record<string, number>`? | 自定义属性当前值，key 为属性 id，对应 `src.key` 的 `c:` 后缀 |
| `state.endingGrade` | `{ grade, score, verdict, items[] }`? | 结算时写入的综合评级 |
| `state.endingKind` | `"manual" \| "ai" \| "bankrupt" \| "finish"`? | `finish` = 时限到期等自然落幕 |

`endingGrade` 只用于游戏内结局页展示，后端原样存取即可，取值说明：

- 有维度：`grade` 为 `S+ / S / A / B / C / D`，`score` 0~100 为各维度均分，`items` 每条对应一个维度。结局规则指定了评级时以指定值为准。
- **无维度**：`grade: "—"`、`score: 0`、`verdict: "旅程结束"`、`items: []`。后端若有校验，请允许 `grade` 为 `"—"`。
- 旧存档里已写入的 `endingGrade`（可能含名气、口碑等旧 items）原样保留，不要迁移。

## 18. 对话修改游戏世界：改动直接落地（字段与接口对齐）

### 18.1 背景（前端已改）

编辑器里的「对话修改」改成了**弹窗**，界面上统一叫「游戏世界」，不再叫「模组」。AI 每轮改动**直接合并进当前世界**，弹窗里**不再有「保存」按钮**，只保留「完成」和「撤销改动」：

- **从生成世界编辑器打开**（平台书架草稿）：点「完成」或点弹窗外，改动写回编辑器的 `mod`。之后沿用现有书架草稿同步，不新增接口。
- **修改玩家自己已保存的世界**：每轮改动立即写入本机用户世界库（`localStorage`，`importModJson`）。目前**不上云**。

### 18.2 【P0】`POST /api/romance/play/complete` 支持工具调用（tools 透传）

**现状问题**：平台登录时，前端调用 `completeWithTools` 不会把 `tools` 发给后端（`src/lib/ai.ts`），只能让模型在正文里输出 ```json 代码块，再由前端解析。模型经常只回文字、不给 JSON，或者 JSON 不完整，结果玩家看到「AI 说改好了」，世界数据却没变（地点 / 人物计数仍为 0）。

**请求新增可选字段**（与 OpenAI Chat Completions 一致）：

```json
{
  "messages": [...],
  "max_tokens": 4000,
  "tools": [{ "type": "function", "function": { "name": "apply_mod_patch", "description": "...", "parameters": { /* JSON Schema */ } } }],
  "tool_choice": "auto"
}
```

**返回新增**：除正文 `content` 外，请原样返回 `tool_calls`：

```json
{ "success": true, "data": { "content": "已加入 6 个 NPC……", "tool_calls": [{ "function": { "name": "apply_mod_patch", "arguments": "{\"content\":{\"npcs\":[...]}}" } }] } }
```

- `arguments` 是 **JSON 字符串**，前端负责解析和容错。
- 底层模型不支持 tools 时：请**忽略** `tools` 正常返回正文，**不要报 400**。前端会退回正文 JSON 解析。
- 计费同普通补全；`tools` 定义的 token 按实际计入即可。
- 后端上线后通知前端，前端删掉 `hasPlatformPlayAuth()` 的跳过逻辑。

**工具 `apply_mod_patch` 参数结构**（供后端做 Schema 透传和日志排查，后端不需要执行）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `manifest` | `{ name?, description?, id? }` | 世界信息，只写要改的字段；`id` 为小写英文，仅新建草稿时生效 |
| `content` | `Partial<ModContent>` | 本轮新增或修改的内容；数组条目必须带 `id`，同 `id` 覆盖旧条目 |
| `remove` | `Record<字段名, string[]>` | 要删除的条目 id |

### 18.3 【P1】书架草稿同步频率会变高

对话每轮都会改 `mod`，「完成」后编辑器触发 `onEditorLiveChange` → `PATCH /api/auth/games/drafts/romance/{fileId}` 以及正文 `PUT .../content`（前端防抖 1.2s）。

- `PUT .../content` 的 `mod` **整包覆盖**（结构见 5.4），对话可能新增 `npcs`、`rooms`、`events`、`fixedEvents`、`worldBook`、`endings`、`creation.paths`、`customAttrs`、`titles` 等任意 `ModContent` 字段。若后端对 `content` 做白名单或裁剪，请**整体放行**。

- 同一 `fileId` 的并发写入以 `updatedAt` 较大者为准，不要报冲突。

### 18.4 【P2】玩家自己改的世界存到服务器（待排期）

**现状**：玩家在「我的世界」里自己改过或另存的世界，现在**只存在当前浏览器里**（`localStorage`），服务器上没有。所以：
